# 7. Техническая архитектура

Источник: линза 4. Все утверждения о поддержке API проверены на 6 сентября 2026 года.

## 7.1 Хранение: куки отвергаются

Требование B25 говорит «хранить в куках браузера». Это придётся изменить, и вот почему.

| Ограничение куки | Последствие |
| --- | --- |
| 4 КБ на одну куку, около 50 кук на домен | Прогресс не помещается |
| Отправка на сервер с каждым запросом | Бессмысленный трафик, сервера нет |
| **Safari ITP режет куки, поставленные из JavaScript, до 7 дней жизни** | Прогресс умирает через неделю |

**Решение: localStorage как источник истины плюс зеркало в IndexedDB.**

Замер объёма: 200 слов около 9 КБ, два года истории около 35 КБ, профиль и настройки остальное. Итого около **47 КБ при лимите 5 МБ**, запас в сто раз. Синхронное чтение localStorage означает, что состояние доступно до первой отрисовки, без скелетонов на старте. Зеркало в IndexedDB стоит тридцати строк и даёт вторую независимую копию, что без регистрации является единственной защитой от потери.

**Версионирование обязательно с первого релиза.** Сервера нет, мигрировать данные можно только клиентским кодом при следующем запуске. Цепочка миграций `MIGRATIONS[v] → v+1`, снапшот перед миграцией, данные из версии новее текущей не затираются.

### Семидневное удаление в iOS Safari

Правило действует с iOS 13.4 и считает дни использования Safari. **Но web-приложение на домашнем экране не является частью Safari и имеет собственный счётчик** (John Wilander, блог WebKit). При ежедневных занятиях счётчик обнуляется постоянно.

Вывод для продукта: **установка на домашний экран — не бонус, а требование сохранности данных.** Онбординг должен продавать её именно так, а не как способ получить иконку.

### Экспорт прогресса

Реальный прогон на 200 словах и 90 днях истории:

| Форма | Размер в base64 |
| --- | --- |
| Наивный JSON | 26 935 символов |
| Компактная: массивы, индекс слова вместо идентификатора, дата как номер дня | **8 300** |

Выигрыш в 3.2 раза. Практический вывод: основной способ переноса — файл, строка остаётся только для короткого варианта без посуточной истории, это около 2 500 символов.

Формат строки: `SHODU-<версия>-<base64url>-<fnv1a>`. Контрольная сумма ловит строку, обрезанную при копировании, **до** того как перезапишет рабочий прогресс.

Ловушка на будущее: индекс слова в компактном экспорте требует стабильного порядка записей в `data/words.json`. Порядок становится частью формата, менять его можно только добавлением в конец.

## 7.2 Установка как приложение

- **Поле `id` в манифесте задаётся сразу и не меняется никогда.** Без него идентификатором приложения становится `start_url`, и его изменение создаёт вторую иконку с потерей данных.
- Режим `standalone`, а не `fullscreen`. На iOS `fullscreen` игнорируется, а часы и заряд батареи в обучающем приложении нужны.
- **Двух значений `theme_color` в манифесте не существует.** Профильное обсуждение в W3C открыто, механизмы `user_preferences` и `media_overrides` не реализованы нигде. Работает только мета-тег с медиавыражением, и Safari его уважает.
- Иконки: `apple-touch-icon` 180 пикселей для iOS, плюс 192 и 512 с назначением `any`, плюс 192 и 512 с назначением `maskable`, где безопасная зона составляет центральные 80%. **Никогда не ставить `"purpose": "any maskable"` на один файл**, нужны два разных.
- `viewport-fit=cover` вместе с `env(safe-area-inset-*)` обязательны, иначе в автономном режиме шапка уедет под часы.

Детект состояния в коде: `matchMedia('(display-mode: standalone)')`, плюс `navigator.standalone` для iOS, плюс маркер в `start_url`. Отдельная ветка нужна для случая **«iOS, но не Safari»**: Chrome и Firefox на iOS не умеют ставить на домашний экран, им нужна подсказка «открой в Safari», а не инструкция по установке.

## 7.3 Service worker

Предварительное кэширование оболочки приложения и стратегия Cache First. Стратегия «отдать из кэша, обновить в фоне» для JavaScript и CSS **не применяется**: она может отдать старый JavaScript вместе с новым CSS.

Против залипания старой версии: service worker **не вызывает `skipWaiting` сам**. Страница видит `registration.waiting`, показывает тост «Доступна новая версия», человек нажимает, страница шлёт сообщение `SKIP_WAITING`, ловит `controllerchange` и делает **ровно одну** перезагрузку. Перед перезагрузкой хранилище сбрасывается на диск дважды. В обработчике активации вызывается `clients.claim`, чтобы офлайн заработал с первой загрузки, а не со второй.

## 7.4 Уведомления: честный вердикт

**Требование B24 в текущей формулировке невыполнимо. Это не сложность реализации, а противоречие в постановке.**

Три независимые причины:

1. Приватный ключ VAPID нельзя положить в статические файлы. Любой, кто откроет исходники, сможет рассылать уведомления вашим пользователям.
2. В протоколе Web Push нет отложенной доставки. Есть поле «сколько хранить», нет поля «доставить в 19:00».
3. Отправлять уведомление должен кто-то в момент, когда приложение закрыто. Если код исполняется только при открытом приложении, уведомление уже не нужно.

Статус нужных API:

| API | Статус на 06.09.2026 |
| --- | --- |
| Web Push на iOS | Доступен с iOS 16.4, **только для приложения на домашнем экране**, только по жесту пользователя, требует VAPID и сервер |
| Declarative Web Push | iOS 18.4 и Safari 18.5, убирает необходимость в service worker, но **сервер всё равно нужен**, планирования нет |
| Notification Triggers, то есть `showTrigger` | **Мёртв.** Google формально прекратил разработку, пробный период закончился на Chrome 83 в 2020 году, в релиз не вышел никогда. Это была ровно та технология, которая решила бы задачу |
| Periodic Background Sync | Только Chromium, требует установки, **минимальный интервал 12 часов**, момент срабатывания не гарантирован. Safari не поддерживает и не планирует, Firefox считает вредным |

Что реально доступно:

| Механизм | iOS | Android |
| --- | --- | --- |
| Точное напоминание в 19:00 при закрытом приложении | только через файл календаря | только через файл календаря |
| Догоняющее уведомление при следующем открытии | да | да |
| Фоновая проверка примерно раз в сутки | нет | да, с разбросом в часы |

**Файл календаря это не костыль, а единственный настоящий ответ на исходное требование.** Событие с правилом повторения `RRULE:FREQ=DAILY` и будильником `VALARM` уходит в системный календарь, приходит точно в 19:00 каждый день, работает при закрытом приложении и без интернета. Время записывается как плавающее, без указания зоны, поэтому 19:00 остаётся 19:00 при переезде в другой часовой пояс.

**Формулировка для интерфейса.** Писать «Пришлём уведомление в 19:00» нельзя, оно не придёт. Правда звучит так: «Напомним, когда откроешь приложение» плюс кнопка «Добавить ежедневное напоминание в календарь». Настоящий push требует минимального бэкенда и выносится в отдельную работу.

## 7.5 Звук

Синтез вместо файлов: ноль килобайт вместо примерно двухсот, нулевая задержка, потому что осциллятор стартует за микросекунды против 50–200 мс у элемента `audio`, а комбо второго, третьего и пятого уровня получаются из одного рецепта с разной высотой.

Формула «нинтендовости»: волна треугольная или синусоидальная, но не прямоугольная; длительность 60–150 мс; **атака 5–12 мс**, а не ноль, иначе слышен щелчок; экспоненциальный спад; фильтр низких частот на 3–6 кГц; интервалы берутся из мажорной пентатоники; питч-бенд вверх на 5–15%; для колокольчиков наград частотная модуляция с неоктавным отношением 3.51.

| Событие | Рецепт |
| --- | --- |
| Тап | треугольник 880 → 660 Гц, 55 мс, громкость 0.16, плюс шум через фильтр высоких частот на 22 мс |
| Верный ответ | треугольник E6 → B6 с призвуком B7, 220 мс |
| Неверный ответ | треугольник 233 → 165 Гц и синус 155 → 110 Гц, фильтр низких на 1.1 кГц. Мягкое «нет», а не зуммер |
| Комбо | `C6 × 2^(n/12)` по пентатонике, от пятого уровня добавляются мерцания колокольчика |
| Алмазы | колокольчик с частотной модуляцией, отношение 3.51, индекс 300, случайная расстройка ±0.6% и джиттер во времени дают живую россыпь |
| Новый уровень | арпеджио от C5 до G6 плюс расстроенный аккорд колокольчиков, 1.5 секунды |
| Сгорание стрика | глиссандо A5 → A3 с закрывающимся фильтром 4000 → 220 Гц и ударом 90 → 55 Гц |

Три отдельные проблемы автовоспроизведения, все закрываются кодом: контекст стартует в состоянии `suspended` и требует `resume` внутри жеста; **на iOS контекст уходит в состояние `interrupted` после возврата из фона** и восстанавливается по событию `visibilitychange`; аппаратный переключатель «без звука» на iOS глушит Web Audio, и обход этого поведения **намеренно не применяется**: выключил звук значит выключил.

В цепи стоит `DynamicsCompressor`, чтобы наложение звука комбо и звука алмазов не давало клиппинга. Одинаковые звуки троттлятся.

## 7.6 Произношение

`speechSynthesis.getVoices()` **возвращает пустой массив при первом вызове**, а на iOS событие `voiceschanged` иногда не приходит вовсе. Поэтому в коде и подписка на событие, и опрос: двадцать попыток по 150 мс. Назначение конкретного голоса на iOS часто игнорируется, на это не закладываемся. Синтезатор зависает в состоянии «говорю» навсегда после ухода вкладки в фон, поэтому по `visibilitychange` вызывается `cancel`. Есть страховочный таймер на случай, когда не приходят ни `onend`, ни `onerror`.

Фолбэк: транскрипция вида `/ˈtʃɒk.lət/` это основной инструмент, а не запасной. Кнопка озвучки скрывается, если синтез недоступен, и прячется до конца сессии после первой ошибки.

## 7.7 Анимации и производительность

Бюджет на среднем Android около **10 мс на кадр** после накладных расходов браузера. Анимируются только `transform` и `opacity`. Свойство `will-change` навешивается **временно**, через класс на время анимации, и снимается по завершении: два десятка постоянных композиторских слоёв заметно тормозят прокрутку.

Кривая сочности `cubic-bezier(.34,1.56,.64,1)` даёт перелёт около 10%. Значения выше 1.8 выглядят дёшево.

Про уменьшенную анимацию: **не «выключить всё», а «убрать движение, оставить обратную связь»**, иначе становится непонятно, засчитан ответ или нет. В обёртке над Web Animations API анимация **сжимается до 1 мс, а не отменяется**, чтобы промис завершения всё равно сработал и логика не сломалась.

Конфетти: пул частиц без выделения памяти в горячем цикле; цикл кадров **полностью останавливается при нуле частиц**; плотность пикселей ограничена двойкой, что на Android с плотностью 3 даёт втрое меньше работы для видеоядра; канва самоуничтожается через 8 секунд; шаг времени нормализуется к 60 кадрам, иначе на экране 120 Гц частицы летят вдвое быстрее. Двести двадцать частиц занимают 2.5–4 мс на кадр на Snapdragon 680.

## 7.8 Структура проекта и деплой

Протокол `file://` не заработает: CORS блокирует модули и запросы, service worker требует безопасного контекста. Разработка идёт через локальный сервер на **`http://localhost`**, именно на этом имени, а не на IP-адресе, потому что localhost считается безопасным контекстом. Проверка на телефоне возможна только по HTTPS, через туннель или деплой-превью.

```
shodu-english/
├── index.html  offline.html  manifest.json
├── service-worker.js        ← обязательно в корне, иначе сузится область действия
├── css/     tokens base components screens animations main
├── js/
│   ├── app.js
│   ├── core/    storage install sw-update sound speech
│   │            reminders motion confetti haptics
│   ├── domain/  srs scoring streak achievements stats   ← без DOM
│   └── ui/      router screen-home screen-session screen-results
│                screen-progress screen-settings components
├── data/    words.json  rules.json  achievements.json
├── icons/   apple-touch-icon-180 · 192/512 any · 192/512 maskable · badge-72
└── screenshots/
```

Слой `domain` не импортирует ни `core`, ни `ui` и ничего не знает о DOM. Это проверяется грепом на `document`, `window` и `localStorage`.

Деплой: Netlify предпочтительнее GitHub Pages, потому что даёт управление заголовками, превью на каждую ветку, что критично для проверки установки на телефоне, и мгновенный откат. Если всё же GitHub Pages, то файл `.nojekyll` обязателен, и при имени репозитория, отличном от `username.github.io`, префикс пути нужен во всех ссылках манифеста, service worker и регистрации. Это самый частый источник поломок, проще подключить свой домен. Роутинг делаем по хешу, а не через History API: так работает одинаково везде.
